# Research: Переключатель порций (UI)

Неизвестных в Technical Context не осталось: стек, тесты и данные известны из репозитория и спеки команды 2. Ниже — решения, которые нужно было принять для реализации.

## R-1. Где хранить выбранный множитель

- **Decision**: в `App` — словарь `{[collectionId]: 1 | 2 | 4}`; отсутствие ключа = ×1. `Shelf` получает `multiplier` и `onSelect`.
- **Rationale**: карточка отрисовывается с `key={c.id}` и размонтируется, когда подборка уходит из выдачи после смены фильтра. Локальное состояние `Shelf` потерялось бы, а FR-011 требует сохранить выбор, когда подборка возвращается. Словарь в памяти не попадает ни в адрес, ни в хранилище браузера.
- **Alternatives considered**: `useState` внутри `Shelf` — теряет выбор при размонтировании; `localStorage` или адрес — запрещены решением Clarifications (Q3).

## R-2. Каким элементом сделать переключатель

- **Decision**: `<fieldset>` с `<legend>Порции</legend>` и тремя нативными `<input type="radio">` (общее `name` на карточку), стилизованными как сегменты; недоступный вариант — `disabled` плюс `aria-describedby` на текст причины.
- **Rationale**: нативная группа radio даёт бесплатно переход стрелками, «выбрано» в программе чтения с экрана и ровно один выбранный вариант (FR-001, FR-014, SC-005). Пользователь выбирает значение, а не выполняет действие — это семантика radio.
- **Alternatives considered**: кнопки с `aria-pressed`, как у чипов бюджета, — визуально единообразно, но стрелки и групповую семантику пришлось бы писать вручную; `role="radiogroup"` на `div` — тот же результат, но больше кода, чем нативный `fieldset`.

## R-3. Как объявлять новый итог

- **Decision**: итог в карточке — `<span aria-live="polite" aria-atomic="true">`; при смене множителя объявляется целиком: «≈ 2 222 ₽ · ×2».
- **Rationale**: FR-014 и SC-005 требуют озвучить новый итог; выбор radio озвучивается сам. Общий `aria-live` на `<main>` объявляет изменения выдачи, но не гарантирует атомарного чтения итога.
- **Alternatives considered**: отдельная скрытая область для объявлений на всю страницу — лишняя сущность для одной строки.

## R-4. Как читать варианты из ответа и что делать с неполными данными

- **Decision**: чистая функция `readVariants(c)` в `frontend/src/servings.ts` возвращает три варианта в порядке 1, 2, 4 или `null`. `null`, если `variants` нет, если это не ровно три элемента с `multiplier` 1, 2, 4, если у варианта нет строки `cart_url` или если в `quantities` нет количества для какого-то товара подборки. При `null` карточка отрисовывается как до фичи.
- **Rationale**: FR-010 требует старого вида на старом бэкенде; неполный ответ — тот же случай выката и не должен ломать страницу. Сбой в одной карточке не влияет на другие.
- **Alternatives considered**: показывать переключатель с частью вариантов — дало бы кнопку, которая обещает корзину ×N без ссылки (SC-002); падать с ошибкой на всю выдачу — несоразмерно.

## R-5. Количества и итог

- **Decision**: UI берёт `variant.total_price` и `variant.quantities[String(xml_id)]` как есть. «было» = `product.base_quantity`, показывается только при `multiplier > 1` и `product.scalable === true`. Форматирование — существующая `qty()` (точка → запятая).
- **Rationale**: FR-003, FR-004; команда 2 гарантирует округление, не больше двух знаков и целые для «шт». Ключи объекта в JSON — строки.
- **Alternatives considered**: брать `product.quantity` и умножать — запрещено (UI ничего не умножает).

## R-6. Имя массива вариантов

- **Decision**: `variants` — окончательное имя (закреплено в `specs/002-servings-logic/research.md` и `contracts/http-api.md`).
- **Rationale**: обе спеки уже использовали это имя; команда 2 сделала его окончательным в своём плане.
- **Alternatives considered**: ждать команду 2 — блокирует работу без необходимости.

## R-7. Ошибки API и `code`

- **Decision**: `getJSON` бросает `ApiError` с `status` и `code` из тела (`{"error", "code"}`); если тело не JSON или `code` нет — `code: undefined`. Видимое поведение страницы не меняется: любая ошибка поиска показывает «Каталог не отвечает…», как сейчас (раздел «Ошибки» спеки). Значения `code` — по `specs/002-servings-logic/contracts/http-api.md`: `invalid_query` (400), `collection_not_found` (404), `internal_error` (500).
- **Rationale**: FR-019 — ветвление только по `code`, не по тексту `error`. Сейчас разного поведения нет, но точка различения готова.
- **Alternatives considered**: разбирать текст `error` — запрещено FR-019; отдельные тексты для 400 — спека их не просит.

## R-8. Пометка «больше бюджета»

- **Decision**: показывать, если `filters.maxPrice > 0` и `total_price` выбранного варианта больше `maxPrice`. Для ×1 при работающем фильтре это не случается, поэтому пометка фактически только у ×2/×4.
- **Rationale**: FR-016, решение 9A: фильтр серверный и по ×1, пометка клиентская.
- **Alternatives considered**: передавать `servings` в поиск — запрещено FR-018.

## R-9. Состояние «Ищем подборки…»

- **Decision**: показывать, пока `result === null` и нет ошибки. При обновлении выдачи прежний `result` остаётся на экране до прихода нового — так уже работает.
- **Rationale**: FR-015; таблица состояний страницы в спеке.

## R-10. Пункт 14 арбитража (пример «≈ 2 222 ₽ · ×2»)

- **Decision**: для реализации не блокирует: UI всегда показывает `total_price` варианта, а пример в спеке — иллюстрация формата. Тесты используют фикстуру с немасштабируемым товаром, где итог ×2 не равен удвоенному.
- **Rationale**: решение по формулировке примера остаётся за человеком; на код оно не влияет.

## R-11. Тестовая стратегия

- **Decision**: сначала тесты, потом код. Модульные тесты `servings.test.ts` (разбор и проверка `variants`, строки состава, бюджет) и сценарные тесты в `App.test.tsx` через роли и доступные имена из [contracts/ui-card.md](contracts/ui-card.md). Фикстура — существующий `breakfast` плюс `variants`, `scalable`, `base_quantity`; отдельная фикстура без `variants` для FR-010. Проверка отсутствия запросов при переключении — по счётчику вызовов `fetch`, как уже сделано в `searches()`.
- **Rationale**: tdd-go покрывает только бэкенд, но AGENTS.md требует TDD для всего MVP; в репозитории фронтенд уже тестируется так же (`App.test.tsx`).
- **Alternatives considered**: e2e в браузере — нет инструментов в проекте, новые зависимости против принципа II.
