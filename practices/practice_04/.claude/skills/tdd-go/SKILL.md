# TDD для Go-бэкенда

Задача skill — не «писать тесты», а **доказать** каждый шаг цикла запуском, а не словами.
Перед первым тестом прочитай [references/writing-good-tests.md](references/writing-good-tests.md).

## Процедура на одно поведение

1. **Требование.** Найди пункт в `docs/requirements.md`. Если его нет — остановись и спроси, не придумывай контракт.
2. **Тест.** Опиши одно поведение через публичный API пакета (`Service`, HTTP-обработчик). Табличный тест, имена подслучаев — по сценарию.
3. **Заглушка.** Если нужного символа ещё нет, добавь минимальную заглушку с сигнатурой и нулевыми значениями, чтобы код компилировался. Красный тест, который не компилируется, ничего не проверяет.
4. **Подтверди red:**
   ```sh
   node .claude/skills/tdd-go/scripts/tdd.mjs red TestИмя --pkg ./internal/collections
   ```
   Нужен вердикт `RED OK`. Остальные вердикты означают, что надо чинить **тест**, а не код:
   - `BUILD FAILED` — добавь заглушку (шаг 3);
   - `PANIC` — тест падает не на проверке; добейся падения через `t.Errorf`/`t.Fatalf`;
   - `ALREADY GREEN` — тест не описывает новое поведение;
   - `NO TESTS` — опечатка в имени теста или пакете.
5. **Минимальная реализация** — ровно столько, чтобы прошёл этот тест.
6. **Подтверди green:**
   ```sh
   node .claude/skills/tdd-go/scripts/tdd.mjs green TestИмя --pkg ./internal/collections
   ```
   Нужен `GREEN OK`: целевой тест прошёл, а `go test ./...` по всему модулю зелёный. `REGRESSION` — сломано соседнее поведение, чини код.
7. **Рефакторинг** при зелёных тестах; после него снова `tdd.mjs green`.
8. **Итог:** `sh scripts/check.sh backend` (gofmt, vet, тесты) и в отчёте — строки из `docs/evidence/tdd-journal.md` за эту задачу.

## Запреты

- Не меняй ожидание в тесте, чтобы он позеленел; меняй код.
- Не удаляй и не пропускай (`t.Skip`) чужие тесты, не ослабляй `scripts/check.sh`.
- Не пиши реализацию раньше подтверждённого `RED OK`.
