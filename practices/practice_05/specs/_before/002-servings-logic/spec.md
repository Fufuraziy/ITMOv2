## Clarifications

### Session 2026-10-21

- Q: Что означает `servings=2` — «вдвое больше подборки из каталога» или «ровно на 2 человека»? → A: множитель к подборке из каталога (1 = как в каталоге, 2 = вдвое, 4 = вчетверо); параметр называется `servings`.
- Q: Умножать на число порций каждый товар подборки или некоторые (кофе, варенье, специи) оставлять как есть? → A: куратор помечает в теме отдельные товары как «не масштабируется»; их количество при любом `servings` как в каталоге, остальные умножаются.
- Q: Что делать, если при 2 или 4 порциях количество товара превышает лимит корзины 40? → A: проверять каталог при старте: масштабируемый товар — базовое количество не больше 10 (×4 ≤ 40), иначе сервис не запускается (формат R1); урезания до 40 и поля `capped` нет.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Подборка на нужное число порций (Priority: P1)

Пользователь открыл подборку «Тыквенный крем-суп» и хочет приготовить вдвое больше. Он запрашивает подборку с множителем порций 2 и получает тот же состав, где количество каждого масштабируемого товара удвоено, товары, помеченные куратором как «не масштабируется» (например, пачка кофе или банка специй), остались как были, а итоговая цена пересчитана по новым количествам.

**Why this priority**: Это суть фичи — без пересчёта количества и цены остальное не имеет смысла.

**Independent Test**: Запросить одну подборку с `servings=1`, `2`, `4` и сравнить количества и `total_price` с базовой подборкой из каталога.

**Acceptance Scenarios**:

1. **Given** подборка с товарами «тыква 2 кг», «лук 0.5 кг», «сливки 1 шт», **When** запрошена подборка по id с `servings=2`, **Then** количества — 4, 1, 2; `servings` в ответе — 2; `total_price` — округлённая сумма `price × новое количество`.
2. **Given** та же подборка, **When** запрошена с `servings=4`, **Then** количества — 8, 2, 4.
3. **Given** любая подборка, **When** запрошена без параметра или с `servings=1`, **Then** количества и `total_price` совпадают с тем, что сервис отдаёт сейчас (до фичи), а `servings` в ответе — 1.
4. **Given** товар в кг с количеством 0.3, **When** запрошено `servings=4`, **Then** количество в ответе ровно `1.2` (без хвостов вида `1.2000000000000002`).
5. **Given** «Завтрак с сырниками», где кофе (1 шт) и варенье (1 шт) помечены как «не масштабируется», а сырники (1 шт) и сметана (1 шт) — нет, **When** запрошено `servings=4`, **Then** сырники и сметана — по 4, кофе и варенье — по 1; у кофе и варенья `scalable: false`, у остальных `scalable: true`.

### User Story 2 - Поиск с учётом порций и бюджета (Priority: P2)

Пользователь ищет подборки «до 2 000 ₽» на 4 порции. Фильтр бюджета и сортировка по цене должны работать по цене уже пересчитанной подборки, иначе в выдаче окажутся наборы, которые на 4 порции стоят дороже бюджета.

**Why this priority**: Бюджет — один из двух главных фильтров (R2); без учёта порций он вводит в заблуждение. Но фича ценна и без поиска (US1).

**Independent Test**: Поиск с `max_price` и `servings=4` возвращает только подборки, чей пересчитанный `total_price` ≤ бюджета; `sort=price_asc` упорядочивает по пересчитанной цене.

**Acceptance Scenarios**:

1. **Given** подборка с базовой ценой 900 ₽, где все товары масштабируются (на 2 порции — около 1 800 ₽), **When** поиск `max_price=1000&servings=2`, **Then** этой подборки нет в выдаче.
2. **Given** та же подборка, **When** поиск `max_price=1000` без `servings`, **Then** подборка в выдаче (поведение как сейчас).
3. **Given** несколько подборок, **When** поиск `servings=4&sort=price_desc`, **Then** порядок — по убыванию пересчитанного `total_price`, при равенстве — порядок каталога.
4. **Given** любой поиск, **When** задан `servings`, **Then** каждая подборка в `collections` уже пересчитана и содержит `servings` с этим значением; `total` — число найденных подборок.

### User Story 3 - Корзина соответствует выбранным порциям (Priority: P1)

Пользователь выбрал 4 порции и нажал «в корзину». В корзине ВкусВилла должно оказаться ровно то, что показано в ответе: те же товары в тех же количествах.

**Why this priority**: Главное обещание сервиса — «одной кнопкой в корзину». Если корзина не совпадает с выбранными порциями, фича вредит.

**Independent Test**: Для каждой подборки и каждого значения `servings` открыть `cart_url` и сверить состав корзины с `products` ответа.

**Acceptance Scenarios**:

1. **Given** подборка запрошена с `servings=1`, **When** пользователь открывает `cart_url`, **Then** это та же ссылка, что сейчас, и корзина совпадает с ответом.
2. **Given** подборка запрошена с `servings=2` или `4`, **When** пользователь открывает `cart_url`, **Then** это заранее созданная куратором ссылка для этого множителя, и в корзине те же товары в тех же количествах, что в `products` ответа.
3. **Given** у одной подборки в каталоге нет ссылки для `servings=4`, **When** сервис запускается, **Then** он не стартует и называет подборку и недостающую ссылку (R1).

---

### User Story 4 - Понятная ошибка при неверном числе порций (Priority: P3)

Кто-то вручную правит адрес страницы или вызывает API с `servings=3`. Сервис не угадывает и не подставляет значение молча, а отвечает ошибкой запроса в том же формате, что и для неверного `max_price`.

**Why this priority**: Защита от тихих ошибок; затрагивает редкие запросы.

**Independent Test**: Набор неверных значений даёт `400` с `error`, начинающимся на `invalid query: `.

**Acceptance Scenarios**:

1. **Given** любой каталог, **When** `GET /collections?servings=3`, **Then** `400 {"error": "invalid query: servings must be one of 1, 2, 4, got \"3\""}`.
2. **Given** любой каталог, **When** `GET /collections/{существующий id}?servings=0`, **Then** `400` того же формата.
3. **Given** несуществующий id, **When** `GET /collections/{id}?servings=abc`, **Then** `400` (параметры проверяются раньше поиска подборки).
4. **Given** несуществующий id, **When** `GET /collections/{id}?servings=2`, **Then** `404 {"error": "collection not found"}`, как в R4.

---

### Edge Cases

- **Предел 40 (R3)**: масштабируемый товар с базовым количеством 15 при `servings=4` дал бы 60. Такой каталог не проходит проверку при старте (FR-006), поэтому в ответе количество никогда не больше 40 и ничего не урезается. Немасштабируемый товар может иметь базовое количество до 40, как сейчас. В текущем каталоге максимальное базовое количество — 5 (×4 = 20), проверку он проходит; ошибка проверяется на тестовом каталоге.
- **Граница 10**: масштабируемый товар с базовым количеством ровно 10 допустим (×4 = 40); 10.01 — нет.
- **Округление `total_price`**: `total_price` при ×2 не обязан быть ровно вдвое больше базового — сумма округляется один раз, после умножения. Пример: базовая сумма 100.4 → 100 ₽; при ×2 сумма 200.8 → 201 ₽, а не 200.
- **Шт и кг**: для «шт» базовые количества в каталоге целые, при ×2/×4 остаются целыми. Для «кг» результат округляется до 0.01 (шаг R3).
- **Все товары немасштабируемые**: количества и `total_price` при любом `servings` как при `servings=1`; `servings` в ответе всё равно отражает запрос, ссылка на корзину — для этого множителя (по составу совпадает с базовой).
- **Немасштабируемые товары и цена**: `total_price(×k)` может быть заметно меньше `k × total_price(×1)` — это ожидаемо, а не ошибка округления.
- **Ссылки и цены**: ссылка на корзину хранит только товары и количества. Если цены во ВкусВилле изменились после сборки каталога, `total_price` в ответе — на дату `updated_at`, как и сейчас.
- **Пустое значение** `servings=` — то же, что отсутствие параметра (как сейчас с `max_price=`).
- **Повтор параметра** `servings=2&servings=4` — используется первое значение (как сейчас для остальных параметров).
- **Похожие на число значения**: `2.0`, `02`, ` 2`, `+2`, `-2`, `x2`, `4 ` — неверные, `400`. Допустимы ровно строки `1`, `2`, `4`.
- **Ничего не нашлось** с `servings` — `200`, `"collections": []`, `"total": 0`, как в R2.
- **Другие методы** — `405`, как сейчас.

## Requirements *(mandatory)*

### Functional Requirements

**Параметр запроса**

- **FR-001**: `GET /collections` и `GET /collections/{id}` MUST принимать необязательный параметр `servings` — множитель порций относительно подборки в каталоге. Допустимые значения — ровно строки `1`, `2`, `4`.
- **FR-002**: Отсутствующий или пустой `servings` MUST означать `1`. Ответ при `servings=1` MUST совпадать с ответом до фичи во всех существующих полях.
- **FR-003**: Любое другое значение MUST давать `400 {"error": "invalid query: servings must be one of 1, 2, 4, got \"<значение>\""}` — тот же формат, что у неверного `max_price`/`sort` в R2. Для `GET /collections/{id}` проверка параметра MUST идти раньше поиска подборки (неверный `servings` + несуществующий id → `400`, а не `404`).
- **FR-004**: При повторе параметра MUST использоваться первое значение.

**Пересчёт количества**

- **FR-005**: Для масштабируемого товара количество в ответе MUST вычисляться так: `round2(quantity_каталога × servings)`, где `round2` — округление до 0.01 по правилу «половина — от нуля». Для товара, помеченного «не масштабируется», количество MUST оставаться как в каталоге при любом `servings`. Порядок товаров, `xml_id`, `name`, `unit`, `price`, `rating`, `url`, `image` MUST не меняться.
- **FR-005a**: Каталог MUST хранить для каждого товара признак «масштабируется» (да/нет); если признак не указан — «да». Признак задаёт куратор в теме, и он переносится в каталог при сборке. Каждый товар в ответе MUST содержать `scalable` (`true`/`false`) — всегда, в том числе при `servings=1`.
- **FR-006**: Проверка каталога при старте (R1) MUST требовать, чтобы у масштабируемого товара базовое количество было не больше 10 — тогда при `servings=4` оно не превышает лимит корзины 40 (R3). Нарушение → сервис не запускается и перечисляет проблему в формате R1, например `<id>: products[2].quantity: scalable must be 0.01-10, got 15`. Для немасштабируемого товара остаётся правило R3 (0.01–40). Урезания количества в момент запроса нет.
- **FR-007**: Количество в ответе MUST сериализоваться как число без артефактов двоичной арифметики: не больше двух знаков после точки, целые — без дробной части (`4`, а не `4.0`).

**Пересчёт цены**

- **FR-008**: `total_price` MUST вычисляться по количествам из ответа (после FR-005): `round(Σ price × quantity_ответа)` до целых рублей, «половина — от нуля» — то же правило, что сейчас для базовой подборки.
- **FR-009**: `price` товара (цена за единицу) MUST не пересчитываться.

**Поиск**

- **FR-010**: В `GET /collections` фильтр `max_price` и сортировка `price_asc`/`price_desc` MUST использовать пересчитанный `total_price`. Фильтры `q` и `tag` от `servings` не зависят. При равных ценах MUST сохраняться порядок каталога.
- **FR-011**: Каждая подборка в ответе (и в поиске, и по id) MUST содержать поле `servings` — применённый множитель (целое `1`, `2` или `4`).

**Корзина**

- **FR-012**: Каждая подборка в каталоге MUST хранить три готовые ссылки на корзину — для `servings` 1, 2 и 4. Их создаёт куратор при сборке каталога через ВкусВилл; сервис в момент запроса ссылок не создаёт и ВкусВилл не вызывает. В ответе `cart_url` MUST быть ссылкой для применённого `servings`; при `servings=1` — та же ссылка, что сейчас.
- **FR-013**: Корзина по ссылке для множителя k MUST содержать ровно товары и количества, которые сервис отдаёт при `servings=k` (FR-005). Для этого куратор MUST считать количества для ссылок по тому же правилу FR-005, что и сервис.
- **FR-013a**: Проверка каталога при старте (R1) MUST требовать все три ссылки у каждой подборки; каждая — по правилу R3 для `cart_url` (начинается с `https://vkusvill.ru/?share_basket=`). Нет ссылки или ссылка неверна → сервис не запускается и перечисляет проблему в формате R1, например `<id>: cart_url[4]: missing`. Отдать `null` или ссылку от другого множителя сервис не может.

**Совместимость и проверка каталога**

- **FR-014**: Правила R1/R3 MUST проверяться на базовой подборке (как сейчас). Пересчитанная подборка MUST удовлетворять R3 по `quantity` (0.01–40) при любом `servings` — это обеспечивает проверка FR-006.
- **FR-015**: `GET /tags` и состав выдачи без `servings` MUST не меняться.

### Key Entities

- **Множитель порций (`servings`)**: целое из набора {1, 2, 4}. 1 — подборка ровно как в каталоге (куратор сам решает, на сколько человек она рассчитана — «на двоих», «четыре порции»); 2 и 4 — в два и четыре раза больше.
- **Базовая подборка**: подборка из каталога — товары и количества, проверенные по R3, плюс три ссылки на корзину (для множителей 1, 2, 4). Не меняется; все пересчёты делаются от неё при каждом запросе.
- **Набор ссылок на корзину**: по одной ссылке `share_basket` на каждый множитель. Создаётся куратором при сборке каталога из количеств по FR-005; ссылка для 1 — нынешний `cart_url`. Точное поле в файле каталога выбирается на этапе плана; наружу отдаётся только одна ссылка — в `cart_url`.
- **Пересчитанная подборка**: базовая подборка с количествами по FR-005, `total_price` по FR-008, полями `servings` и `scalable`, `cart_url` — ссылкой для применённого множителя (FR-012).
- **Товар в подборке**: добавляется признак «масштабируется» (`scalable`, задаёт куратор, по умолчанию «да»). У масштабируемого товара базовое количество 0.01–10, у немасштабируемого — 0.01–40 (R3).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Для 100% подборок каталога и всех трёх значений `servings` количество каждого масштабируемого товара равно `базовое × servings` (с точностью 0.01), а каждого немасштабируемого — базовому; ни одно количество в ответе не больше 40.
- **SC-002**: Для 100% ответов `total_price` отличается от точной суммы `price × quantity` по товарам ответа меньше чем на 1 ₽.
- **SC-003**: Ответы без `servings` и с `servings=1` совпадают с ответами до фичи во всех существующих полях — 0 отличий на всём каталоге.
- **SC-004**: 100% неверных значений из набора граничных случаев (0, 3, -2, 2.0, 02, пробелы, буквы) отвергаются с `400`; 0 случаев тихой подстановки значения по умолчанию.
- **SC-005**: Ни одна подборка в поиске с `max_price=N&servings=k` не имеет пересчитанной цены больше N.
- **SC-006**: 100% подборок каталога имеют ссылки на корзину для всех трёх значений порций; для каждой выдаваемой ссылки состав корзины совпадает с `products` ответа (проверка вручную на 3 подборках × 3 значения порций).

## Assumptions

- **«Порция» = множитель к подборке из каталога**, а не абсолютное число едоков (решено в Clarifications): в каталоге нет поля «на сколько человек», а в `docs/features.md` фича описана как «Порции ×2 / ×4». Абсолютный счёт («на 1 человека» для подборки «на двоих») с полем в темах куратора и дробными множителями — вне этой фичи.
- **Лимит 40 проверяется при сборке, а не при запросе** (решено в Clarifications): сервис никогда не отдаёт урезанную корзину. Если куратору нужен масштабируемый товар больше 10, он уменьшает базовое количество или помечает товар «не масштабируется».
- **Одно округление цены**: `total_price` округляется один раз от суммы, как сейчас; поэтому `total_price(×2)` может отличаться от `2 × total_price(×1)` на 1 ₽.
- **Значения 1/2/4 фиксированы**: другие множители (3, 6) не входят в фичу и отвергаются.
- **Ссылки создаются при сборке каталога**: сервис остаётся «только чтение» и не зависит от ВкусВилла во время запросов. Цена — сборка каталога создаёт 3 корзины на подборку вместо одной.
- **Сборка каталога**: в темах куратора (`catalog/themes.json`) появляется пометка «не масштабируется» у отдельных товаров; скрипт куратора (`curate.mjs`) переносит её в каталог и создаёт три корзины по правилу FR-005, после чего каталог пересобирается (руками каталог не правится). До пересборки нынешний каталог не пройдёт проверку FR-013a — пересборка входит в фичу.
- **Контракт**: фича добавляет пункт в `docs/requirements.md` (условно R7) и меняет модель и R3: у подборки появляются ссылки на корзину для каждого множителя, у товара — признак «масштабируется» и правило «масштабируемый товар — не больше 10». Это защищённый файл — правка только по поручению человека после приёмки спеки.
- **Вне фичи**: интерфейс (команда 1), MCP-инструменты `search_collections`/`get_collection` (параметр порций можно добавить отдельно), `/tags`.

## Что я гарантирую UI

Договор между логикой (команда 2) и интерфейсом (команда 1). Всё, что не перечислено здесь, UI не должен считать стабильным.

### Запрос

| что | значение |
|---|---|
| Параметр | `servings` в строке запроса `GET /collections` и `GET /collections/{id}` |
| Допустимо | ровно `1`, `2`, `4` |
| По умолчанию | нет параметра или `servings=` → `1` |
| Совместимость | с `q`, `tag`, `max_price`, `sort` — любые сочетания |

### Ответ `200`

`GET /collections?servings=2` → `{"updated_at": "2026-10-06", "total": N, "collections": [<подборка>, ...]}` — внешняя обёртка как в R2.

`GET /collections/{id}?servings=2` → `<подборка>`.

Подборка:

| поле | тип | гарантия |
|---|---|---|
| `id`, `title`, `description`, `tags` | как сейчас | от `servings` не зависят |
| `servings` | целое | **новое**; всегда есть; `1`, `2` или `4` — применённое значение |
| `total_price` | целое, ₽ | уже пересчитано под `servings`; UI ничего не умножает |
| `cart_url` | строка | всегда есть, никогда не `null`; начинается с `https://vkusvill.ru/?share_basket=`; ведёт на корзину ровно с `products` этого ответа (товары и `quantity`) для применённого `servings`. При `servings=1` — та же ссылка, что сейчас. Ссылки для разных `servings` различаются — UI берёт `cart_url` из ответа на тот `servings`, который показывает |
| `products` | массив | тот же порядок и состав, что при `servings=1` |

Товар:

| поле | тип | гарантия |
|---|---|---|
| `xml_id`, `name`, `unit`, `price`, `rating`, `url`, `image` | как сейчас | от `servings` не зависят; `price` — за `unit` |
| `quantity` | число | уже пересчитано; 0.01–40 при любом `servings` (ничего не урезано); ≤ 2 знаков после точки; целое для «шт» |
| `scalable` | bool | **новое**; всегда есть; `false` — количество не зависит от `servings` (куратор пометил товар как «не масштабируется») |
### Ошибки

| код | когда | тело |
|---|---|---|
| `400` | неверный `servings` (а также `max_price`, `sort`, как раньше) | `{"error": "invalid query: …"}` |
| `404` | нет подборки с таким id (при верном `servings`) | `{"error": "collection not found"}` |
| `405` | метод не GET | как сейчас |
| `500` | внутренняя ошибка | `{"error": "internal error"}` |

UI опирается на код ответа и префикс `invalid query: `; текст после префикса — для отладки, может меняться.

### Чего UI не делает сам

- Не умножает `quantity` и `total_price` — берёт из ответа.
- Не фильтрует по бюджету после получения выдачи — `max_price` уже учтён с порциями.
- Не собирает и не подменяет ссылку на корзину: после смены порций берёт `cart_url` из нового ответа, а не из старого.
