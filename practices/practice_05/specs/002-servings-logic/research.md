# Research: масштабирование подборки по порциям (логика)

В Technical Context не осталось `NEEDS CLARIFICATION`. Ниже — решения, которые спека оставила плану («Открытые вопросы», «точное поле в файле каталога выбирается на этапе плана»), и неочевидные места реализации.

## R-1. Где в каталоге хранятся ссылки ×2 и ×4

- **Decision**: в подборке остаётся `cart_url` (×1, как сейчас) и добавляется объект `cart_urls` с ключами `"2"` и `"4"`. Другие ключи — ошибка каталога.
- **Rationale**: ×1 не меняется ни в файле, ни в ответе (FR-002, SC-003); `TestLoad`, MCP-сервер и старый фронтенд читают `cart_url` как раньше. Ключи-строки совпадают со значениями `servings` в запросе.
- **Alternatives considered**: `cart_urls` с ключами 1/2/4 вместо `cart_url` — ломает формат каталога и существующий тест уникальности ссылок; отдельные поля `cart_url_x2`/`cart_url_x4` — при новом множителе меняется схема, а не данные.

Сообщения проверки: `<id>: cart_urls[2]: missing`, `<id>: cart_urls[4]: must start with https://vkusvill.ru/mobile?basket&share=`, `<id>: cart_urls[3]: unknown servings, want 2 or 4`. Пример `cart_url[4]` в FR-013a спеки приведён к этому виду.

## R-2. Как в каталоге хранится «не масштабируется»

- **Decision**: у товара в каталоге и в теме необязательное `"scalable": false`. Нет поля или `true` — товар масштабируется. Куратор и `curate.mjs` пишут поле только при `false`.
- **Rationale**: по FR-005a признак по умолчанию «да»; 12 подборок не нужно переписывать целиком, а каталог остаётся читаемым. В Go поле — `*bool`, чтобы отличить «нет поля» от `false` (каталог разбирается с `DisallowUnknownFields`, поэтому поле должно быть объявлено).
- **Alternatives considered**: `"fixed": true` (инверсия) — тогда в каталоге и в ответе одно понятие называлось бы по-разному; обязательный `scalable` у каждого товара — шум в 59 товарах.

## R-3. Имя массива вариантов и коды ошибок (согласуется с командой 1)

- **Decision**: массив — `variants` (рабочее имя становится окончательным; так он уже назван в обеих спеках). Значения `code`:

  | HTTP | `code` | когда |
  |---|---|---|
  | 400 | `invalid_query` | неверный `servings`, `max_price` или `sort` |
  | 404 | `collection_not_found` | нет подборки с таким id |
  | 500 | `internal_error` | внутренняя ошибка |

- **Rationale**: UI (спека 001, FR-019 и таблица ошибок) различает три ситуации: ошибка запроса, нет подборки, сервис не отвечает. Один код на ситуацию; какой именно параметр неверен — в тексте `error`. `snake_case` — как остальные поля ответа.
- **Alternatives considered**: коды на каждый параметр (`invalid_servings`, `invalid_max_price`) — UI их не различает, а контракт разрастается; числовые коды — хуже читаются в логах.
- `405` остаётся как сейчас (ответ `net/http` без JSON) — FR-016 его не касается.

## R-4. Модель ответа: отдельный тип, а не поля в `Collection`

- **Decision**: `collections.Collection`/`Product` остаются моделью каталога и хранилища (+ `CartURLs`, `Scalable`). Ответ — новые типы `ScaledCollection`, `ScaledProduct`, `Variant`, которые строит чистая функция `Scale(c Collection, s Servings) ScaledCollection`. `Service.Search`/`Get` и `Store` не меняют сигнатур; `Query` получает `Servings` (нулевое значение = 1).
- **Rationale**: в каталоге `scalable` необязателен, в ответе обязателен; `variants`, `servings`, `base_quantity` не должны приниматься из файла каталога (иначе `DisallowUnknownFields` перестанет ловить опечатки куратора). Неизменные сигнатуры — существующие тесты компилируются и проходят без правок ожиданий. `Scale` — публичная функция, её удобно тестировать таблицей (style guide, правило 1).
- **Alternatives considered**: добавить выходные поля в `Collection` — каталог начнёт принимать `variants`; менять `Search` на `[]ScaledCollection` — ломает хелперы существующих тестов.

## R-5. Округление количества и одинаковый результат в Go и JS

- **Decision**: `round2(x) = round(x × 100) / 100`; Go — `math.Round` (половина от нуля), JS — `Math.round` (половина вверх). `total_price` — `math.Round(Σ price × quantity)` по уже округлённым количествам (переиспользуется `totalPrice` из `memory_store.go`).
- **Rationale**: количества и множители положительные, поэтому правила совпадают. Базовые количества имеют не больше двух знаков (шаг R3), множители целые — точный результат тоже имеет не больше двух знаков, и округление только убирает двоичный «хвост» (`0.3 × 4 = 1.2000000000000002` → `1.2`). Пограничных половин не бывает, поэтому корзина куратора и ответ сервиса совпадают (FR-013). `encoding/json` печатает `1.2` и `4` без лишних знаков (FR-007).
- **Alternatives considered**: целочисленная арифметика в сотых — точнее, но тип `quantity` в каталоге и API — число с плавающей точкой, и пришлось бы конвертировать на границах; выигрыша при k ∈ {1, 2, 4} нет.

## R-6. Варианты: считать на лету или заранее

- **Decision**: `Scale` считает три варианта на каждый ответ, без кэша. `Search` для фильтра и сортировки берёт цену для `q.Servings` той же функцией.
- **Rationale**: 12 × 20 × 3 операций — пренебрежимо; нет состояния, которое надо держать согласованным с каталогом. При переходе на Postgres логика не меняется.
- **Alternatives considered**: предрасчёт в `NewMemoryStore` — лишнее состояние и копирование ради микросекунд.

## R-7. Порядок выката, чтобы проверки оставались зелёными

Проблема: новый каталог (`cart_urls`, `scalable`) не разберёт текущий бэкенд (`DisallowUnknownFields`), а обязательные `cart_urls` не пройдёт текущий каталог.

- **Decision**: три шага, после каждого `sh scripts/check.sh` → `CHECK PASS`:
  1. **Бэкенд принимает новые поля каталога, но не требует их**: `Collection.CartURLs`, `Product.Scalable`; формат ссылок и ключей проверяется, если они есть; правило ≤ 10 для масштабируемых (текущий каталог проходит: максимум 5). Ответ API не меняется.
  2. **Куратор**: `themes.json` (+ `scalable: false`), `curate.mjs` (3 корзины, `cart_urls`), `--dry-run`, затем пересборка `collections.json`.
  3. **Бэкенд требует ссылки и отдаёт порции**: FR-013a — отсутствие `cart_urls[2]`/`[4]` становится ошибкой (фикстуры тестов получают ссылки); `TestLoad` проверяет уникальность всех ссылок; затем `ParseServings`, `Scale`, `variants`, поиск по цене для `servings`, `code` в ошибках. К этому моменту у каждой подборки гарантированно есть все три ссылки, поэтому состояния «ссылки нет» в коде ответа не бывает.
- **Rationale**: каждый шаг проверяем отдельно; снаружи фича появляется только после шага 3 и выходит одним релизом с пересборкой каталога (решение 6A).
- **Alternatives considered**: всё одним шагом — между правкой кода и пересборкой каталога проверки красные, а TDD-скрипт не даст подтвердить GREEN.
